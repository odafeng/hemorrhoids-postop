# 0002. CRF 以 DB 匯出為準，紙本只留無法自動生成的欄位

日期：2026-08-29

## 狀態

已接受。取代先前「CRF 由研究人員逐例手動謄寫」的隱含做法。

## 背景

`收案文件/個案報告表_CRF紀錄.xlsx` 有九個分頁，設計上是獨立於資料庫的紙本紀錄。
收案自 2026-07-23 開始，到 2026-08-29 已有 11 例，CRF 的實際狀態是：

- `表單一_收案登記`：1 列
- `個案總覽`：1 列，且停在「實際 8／應 9」的舊值
- `表單二_每日症狀回報`：8 列，全部屬同一例；該例在 DB 裡有 13 筆
- `表單三_警示處理紀錄`：3 列，處理結果與處理人員多半空白
- `表單四_醫療利用紀錄`：0 列
- `表單六_結案退出`：0 列，儘管已有一例於 2026-08-22 結案

同一批資料在 Supabase 是完整的。CRF 落後不是因為資料沒收到，而是雙寫本來就會漂移，
而漂移沒有任何一端會報錯。這與 `pii_patients` 和收案對照表的關係是同一個模式，
2026-08-14 曾因此漏掉三例的 PII。

## 決策

資料庫是 source of truth。CRF 只承載資料庫生不出來的欄位，其餘由腳本從匯出檔填入。

- 自動欄由 `prototype/scripts/crf_fill.py` 每次覆寫；手填欄腳本永不觸碰。
  欄位逐一分類見 `docs/superpowers/specs/2026-08-29-crf-export-design.md`。
- 腳本不連資料庫，輸入是研究人員 Dashboard 既有「完整備份」功能匯出的 JSON。
  資料存取仍只有一條路徑，不新增金鑰，也不新增一份 RLS 之外的讀取管道。
- 應回報數與依從率取 `v_adherence_summary`，不在腳本內重算。回報日規則的單一定義是
  `fn_report_days()`，前端 `isReportDay()` 已經是它的鏡像，再寫第三份必然三方不一致。
- 不新增任何 DDL。醫療利用補的是既有表的 insert 路徑；`alerts` 缺的四個處理欄位
  需要 `ALTER TABLE`，收案期間不做，維持手填。

## 後果

好處：

- CRF 與資料庫的落差從「靠人記得謄寫」變成「重跑一次腳本」。
- 缺漏會浮出來。腳本啟動時驗證 `surgical_records` 涵蓋率，缺哪幾例直接中止並列名，
  不再是工作簿裡一格看不出來的空白。
- 每日症狀回報這類逐列資料不再需要人工抄寫，抄錯的可能性一併消失。

代價與風險：

- 就地更新既有工作簿，寫入邏輯有 bug 時會碰到手填資料。以每次執行前自動備份、
  以及對位鍵改用 `study_id` 而非列號來降低風險，但無法歸零。
- 備份檔必須由 PI 帳號下載。`surgical_records` 的 researcher policy 是
  `researcher_read_own_surgeon`，非 PI 下載會少列。涵蓋率檢查擋得住，但這是流程上的限制。
- 年齡、性別、BMI 三欄在資料庫沒有寫入端，本次維持手填，收案結束後回溯補登。
  在那之前 `v_adherence_summary` 的這三欄仍是空的。
- CRF 從「獨立的紙本紀錄」變成「資料庫的衍生物」。若 IRB 稽核要求 CRF 能獨立成立，
  這個決定要重新檢視。目前的判斷是簽名與臨床判讀留在紙本已足夠。
