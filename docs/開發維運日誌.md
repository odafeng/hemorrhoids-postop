### bug + db · 研究者儀表板警示「確認」按鈕沒反應
- **症狀**：研究者/PI 按警示「確認」完全沒反應。
- **根因**：正式資料庫 `alerts` 表缺 `acknowledged_by` 欄位——補該欄位的 migration
  `20260326070000_alert_acknowledge_cols.sql` 因 migration 版本錯位（靠手動套用）**從未套進
  production**；前端 `acknowledgeAlert()` 寫入該欄位時 Postgres 回 `42703`，被前端 catch
  吞掉只留 `console.error`，畫面零回饋。
- **修法（正式資料庫變更）**：經 Management API 手動對 production：
  1. `ALTER TABLE alerts ADD COLUMN IF NOT EXISTS acknowledged_by TEXT;`（純新增欄位）
  2. 新增 `researcher_ack_alerts` UPDATE policy——原本 `alerts` 僅 `pi_manage_alerts`（限 pi）
     可寫，故新增讓 researcher 也能確認**自己主刀醫師病人**的警示（沿用現有 surgeon 範圍模型）。
- **影響**：**不需前端部署**；補完後 PI/researcher 於 App 內按「確認」即正常生效並寫入
  `audit_trail`。以 `id=-1` 空更新驗證 `42703` 已消除、未動任何真實資料。
- **附註**：本次亦確認 **production RLS 與磁碟 `base_schema` 不一致**（prod 的
  `researcher_read_alerts` 為 surgeon 綁定）——正式環境 RLS 須以 `pg_policies` 直接查詢為準，
  勿以磁碟 migration 為權威。
- **紀錄**：migration `prototype/supabase/migrations/20260726000000_researcher_ack_alerts.sql`；
  commit `84ea236`。

### ops · ai-chat uptime 主動監控（health endpoint + Healthchecks.io）
- **需求**：ai-chat 是臨床介入，收案期間不能默默斷線。最陰險的失效是 Anthropic 用量上限——
  首頁照樣 200、聊天卻 400/500，ping 首頁抓不到。既有 health 函式只驗 `CLAUDE_API_KEY`
  有沒有設，驗不到「通不通 / 有沒有額度」。
- **做法**：health 函式改為**主動 canary**——用與 ai-chat 同一把 `CLAUDE_API_KEY` 打
  `max_tokens:1` 真生成（撞得到用量上限）＋ `rag_documents` count（不回傳 PII）＋ OpenAI
  `/v1/models`（非致命）。邏輯以依賴注入寫在 `checks.ts`、單元測試 10/10；`index.ts` 為薄殼。
  加 `HEALTH_TOKEN` query gate（未帶 token 回 401，擋未授權觸發付費呼叫）。
  `.github/workflows/uptime.yml` 由每 6h 升級為 `*/5` 探測＋重試，成敗回報 Healthchecks.io
  （dead man's switch + 手機告警）。
- **影響（正式環境）**：`supabase functions deploy health --no-verify-jwt` 部署到 prod
  （**純附加、不碰 ai-chat 介入、無前端變更 → 不需 banner**）；設 Supabase secret
  `HEALTH_TOKEN`、GitHub secrets `HEALTH_TOKEN` / `HC_PING_URL`。
- **驗證**：prod 冒煙 no-token→401、with-token→200 healthy（修復後）；本地 `deno test` 10/10。
- **紀錄**：spec `docs/superpowers/specs/2026-07-26-ai-chat-uptime-monitoring-design.md`、
  runbook `prototype/supabase/functions/health/README.md`；commit `ccc7eaf`→`06dd74c`。
- **剩餘手動**：Healthchecks.io 後台把 Integrations 接到 ntfy。

### incident · Anthropic 用量上限導致 ai-chat 對病人停機
- **發現**：上述監控**上線第一輪冒煙測試即抓到**——Anthropic 回 `HTTP 400`：
  「You have reached your specified API usage limits. You will regain access on
  2026-08-01 00:00 UTC.」
- **根因**：Anthropic 帳號達到**自訂的每月用量/花費上限**；ai-chat 與 canary 共用同一把 key，
  故病人端 AI 問答同步失效——典型「網站活著、聊天壞掉」的靜默停機。
- **影響**：AI 問答中斷（靜態衛教內容仍在 PWA，不完全開天窗）。若不處理將持續到
  8/1 00:00 UTC 自動重置。
- **處置**：PI 於 Anthropic Console 調高每月上限 → **立即恢復**；health endpoint 下一輪
  自動翻回 200 healthy（已實測確認）。
- **可重演風險**：上限每月重置，收案量若再撞上會再次靜默停機——監控會再告警，但根治須把
  上限設在高於單月收案用量。

### ops · uptime 探針改用 Better Stack（退役 GitHub Actions cron）
- **症狀**：Healthchecks.io 的 check 一直 UP/DOWN flapping，但 ai-chat 實測 healthy。
- **根因**：workflow 設 `*/5`，但 GitHub 對高頻 scheduled workflow 大幅節流，**實際約每
  29 分才跑一次**（12:11→12:40→13:10）；HC 卻設「每 5 分該收到心跳」（period 5m + grace
  6–8m），中間 ~24 分收不到 ping → dead man's switch 判 DOWN → 下次 run 又 UP。屬監控設定
  假象，非服務跳動。（唯一真 DOWN 是 12:40 撞到 Anthropic 用量上限那次。）
- **處置**：退役 `.github/workflows/uptime.yml`、移除其 GitHub secrets（`HEALTH_TOKEN`、
  `HC_PING_URL`）；改用 **Better Stack 主動探針**直接打 token'd `health` endpoint。health
  函式與 `HEALTH_TOKEN` 不變。
- **影響**：無前端、無 ai-chat 變更；commit `d21a8b8`。Better Stack 帳號/monitor 由 PI 設定
  （指向 health URL、非 2xx 即 DOWN、告警接手機）；HC check 應暫停/刪除以免持續假 DOWN。
- **教訓**：GitHub scheduled workflow 是 best-effort，不適合做緊間隔 liveness 探測。
