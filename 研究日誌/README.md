## 格式

每日一個 YAML 檔案，命名為 `YYYY-MM-DD.yaml`。結構化欄位方便程式解析（統計進度、產生報表），同時人類可直接閱讀。

檔案位於公開 repo。受試者姓名、病歷號、聯絡方式、email 與任何金鑰一律不寫入，僅以 Study ID、角色或收件端類型指涉。

### 寫的時候優先寫這五項

其餘內容（改了哪些檔、跑了哪些測試、commit 編號）git 都查得到，寫多了只會稀釋下面這五項。寧可一則兩行寫出來，不要一則十欄拖到隔天忘記。

1. **被推翻的假設，以及推翻它的是什麼**（`hypotheses_ruled_out`）。日誌若只記通往答案的那條線，死路會全部流失，下一個人得重走一次。例：08-12 記下「不是 template 缺變數，PI 貼出的 template 確含該變數」，這一句省掉的是重跑一次的第一個小時。要在假設被推翻的當下寫，事後回想一定會漏。
2. **刻意「不」做什麼，以及理由。** 擋掉重新爭論。例：08-12 決定不把 TEST-001 排除於提醒與 CSV 匯出。
3. **驗證涵蓋到什麼範圍**，不只是通過與否。日誌記的是「你驗證了什麼」，讀起來卻會像「這件事沒問題」——08-05 記下 production recovery 驗證通過，實際只涵蓋一種收件端，七天後在 Gmail 上失效。寫下當時的條件，日後才判斷得出覆蓋範圍。
4. **怎麼驗的**，尤其當直覺做法會出錯時。例：比對 bundle 字串而非 hash。
5. **下次的警覺點。** 這一項若夠通用，另外收進 [lessons_learned.json](lessons_learned.json) 的 `recurrence_signals`。

收進 `lessons_learned.json` 的門檻是兩個條件同時成立：換個專案還成立（`scope: general`），而且講得出具體的復發徵兆。多數日子產不出這種教訓，不必強求。
