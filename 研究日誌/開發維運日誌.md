## 2026-08-05

### incident + bug + ops · 新增研究人員後邀請信未送達（Supabase default SMTP 限制）

- **症狀**：PI 於研究者儀表板使用「新增研究人員」後，Supabase Auth 已留下受邀帳號，
  但收件人沒有收到邀請信；該帳號持續為 `email_confirmed=false`、`last_sign_in_at=null`。
  單看「Auth user 已建立」不足以證明郵件有送出或送達。
- **實際根因**：專案仍使用 Supabase 的 default SMTP。自 2024-09-26 起，未設定 Custom SMTP
  的專案只能寄 Auth 信件給 Supabase organization members，外部研究人員會得到
  `email_address_not_authorized`。本機 `.env` 雖已有 `RESEND_API_KEY`，但 Supabase Auth 是在
  Supabase 託管環境送信；只把 key 放在 App 的 `.env`，**不會自動把 Resend 接到 Auth**。
  參考：Supabase [Custom SMTP](https://supabase.com/docs/guides/auth/auth-smtp) 與
  [default provider policy](https://supabase.com/changelog/29370-supabase-auth-changes-to-default-email-provider)。
- **次要缺陷（錯誤被誤分類）**：`researcher-invite` 原本把所有 HTTP 422 都翻成「已經註冊過」。
  因此 SMTP 未設定、驗證錯誤或未來其他 422 都可能被誤報為 duplicate email，遮蔽真正根因。
- **第三個缺口（不可恢復）**：帳號一旦已建立但信沒寄出，原 UI 只有停用／啟用，沒有重寄。
  再按「新增研究人員」只會遇到既有帳號，無法讓該人完成首次設定密碼。

**調查與決策順序**

1. **先證明不是收件匣主觀問題**：查 Auth user 狀態、Supabase Auth 錯誤語意與寄送政策，
   確認目標帳號從未確認、從未登入，且專案沒有 Custom SMTP；故不以「請查垃圾信」作結論。
2. **沿用既有 Resend，不另建 SMTP 供應商**：已有可用 API key，Resend 官方亦直接支援
   Supabase SMTP（`smtp.resend.com:465`、username `resend`、password 為 API key）。
   另開供應商只增加金鑰、DNS 與監控面，對本次問題沒有額外價值。
3. **寄件網域選 `shihfenghuang.com` 根網域**：原先偏好 `auth.shihfenghuang.com` 以隔離 Auth
   reputation，但 Resend Free plan 僅允許 1 個 domain，建立第二個 domain 時 API 回 403。
   因此使用既有 root domain；若日後升級方案，再考慮把 Auth 搬至專用 subdomain。
4. **不放寬既有 DMARC／root SPF**：Squarespace Domains 上原有 `_dmarc` 為 reject policy、
   root SPF 為 `-all`。Resend 使用獨立的 `send.shihfenghuang.com` MAIL FROM 與
   `resend._domainkey` DKIM，故只新增三筆 additive records，不改既有政策：
   - `resend._domainkey` TXT（DKIM；公鑰值不重複寫入日誌）
   - `send` MX → `feedback-smtp.ap-northeast-1.amazonses.com`，priority 10
   - `send` TXT → `v=spf1 include:amazonses.com ~all`
5. **DNS 先 verified，再啟用 SMTP**：公開 resolver 與 authoritative nameserver 都解析正確後，
   才呼叫 Resend verify。最終 DKIM + 兩筆 SPF 全部 `verified`，region `ap-northeast-1`。
   Open/click tracking 維持 `false`，避免 Auth 信件加入非必要追蹤。
6. **Browser automation 失敗時不取用 session/cookie**：Chrome、extension 與 native host 診斷
   均正常，但 Browser connector 無法建立通訊。未改走 cookie extraction 或非授權 UI scripting；
   改由 PI 在 Squarespace 貼入上述三筆**公開 DNS 值**，其餘 API 設定仍由維運端完成。
7. **保留既有 Auth 行為，只補 SMTP**：官方 Management API 範例會示範
   `mailer_autoconfirm=false`，但本 App 的病人註冊流程依賴既有 `true`；本次刻意不照抄該欄位。
   只設定 SMTP sender／host／port／user／password 與 rate limit，並確認 Site URL、redirect allow
   list、`mailer_autoconfirm=true` 均未變。Management API 實際要求 `smtp_port` 為字串；第一次以
   number 送出得到 HTTP 400、**未套用任何變更**，改為 `"465"` 後 HTTP 200。

**程式修正**

  `email_exists`→409、`email_address_not_authorized`→503、

  service role 讀取真正 email，並驗證 target 的 `app_metadata.role` 必須是 `researcher`／`pi`。

## 2026-08-02

### bug · 每日提醒推播未依同意之追蹤排程
- **症狀**：`check-adherence` 對 POD 0–30 **每天**推播「尚未填寫症狀回報」，未判斷當日是否為回報日。
  受試者於非回報日仍被催促，與同意書所載頻率不符。
- **修法**：新增 `fn_report_days()`（`SETOF INTEGER`，回傳 `[0–7, 9, 11, 13, 20, 27]` 共 13 天）
  作為排程的**單一定義**，並將 `fn_expected_reports()` 改建於其上——如此依從率分母與提醒排程
  不可能分歧。Edge Function 啟動時以 RPC 取一次該集合。
- **刻意不在 TypeScript 再寫一份**：今日已因「同一規則存在兩處實作」產生兩個缺陷
  （警示引擎 JS/PL-pgSQL、依從率檢視磁碟/prod），不再新增第三份。
- **失敗處理**：RPC 失敗或回傳空集合一律 `throw`。預設「每天提醒」會退回原本的錯誤行為；
  預設「都不提醒」則會無聲關閉追蹤提醒——兩者都是靜默失敗，故選擇讓 cron 明顯報錯。
- **順帶改善**：排程過濾移到迴圈之前，非當日到期者不再各發 2 次資料庫查詢。
- **測試**：新增 `check-adherence/schedule.test.ts`（5 項，涵蓋三個週期、觀察期外、多人混合）。
  另實測 PostgREST 對 `SETOF INTEGER` 之回傳形狀為純量陣列 `[0,1,...]`，確認 `.map(Number)` 正確
  ——此為單元測試涵蓋不到的整合點。
- **正式資料庫變更**：`fn_report_days()` 與改寫後之 `fn_expected_reports()` 經 Management API 套用，
  已驗證回報日集合與依從率數值不變。migration `20260802160000_report_day_schedule.sql`。

### bug + db · 依從率檢視 join 扇出 ＋ 分母未依同意書之追蹤排程
- **發現經過**：建立 CRF 個案紀錄工作簿時，欲引用 `v_adherence_summary` 取回報次數，
  發現 HSF-001 顯示 `total_reports = 24`、`adherence_pct = 240%`，但實際僅 8 筆症狀回報。
- **缺陷一（join 扇出）**：該檢視自 `patients` 同時 LEFT JOIN `symptom_reports` 與 `alerts`，
  兩個獨立的一對多 join 使每筆回報被警示筆數乘一次（8 × 3 = 24）。
  **膨脹倍率等於各受試者的警示數，故警示愈多者依從率愈高——屬系統性偏差而非隨機誤差。**
  `alerts` 僅供 `had_alerts` 使用，改為 `EXISTS` 子查詢即解。
  （`avg_pain`/`min`/`max` 因每列等倍複製而未受影響，惟 `total_reports`、`adherence_pct` 失真。）
- **缺陷二（分母定義）**：原分母為 `max(pod) + 1`，即假設每日皆須回報。惟**受試者同意書**
  （`ConsentPage.jsx`）載明之排程為「第 0–7 天每日、第 8–14 天每 2 天一次、第 15–30 天每週」，
  經主持人於 2026-08-02 確認為「第一週每日、第二週每兩日一次、第三週起每週一次」。
  另原分母以 `max(pod)` 為基準，導致**中途失聯者反而得到 100%**（於 POD 3 停止回報、現已 POD 20
  者，分母僅 4）——這正是依從率指標最該抓到的情形。改以**術後經過天數**為基準。
- **編碼結果**：POD 0–7 每日（8 次）→ POD 9、11、13（3 次）→ POD 20、27（2 次），30 天共 13 次。
  已逐日驗證曲線。**解讀選擇（供主持人覆核）**：第二週自最後一次每日回報（POD 7）起算 +2 天，
  落在 9/11/13 而非 8/10/12/14；第三週起自 POD 13 起算 +7 天。
- **過程中發現的 migration 錯位實例**：磁碟上早有 `20260326060000_protocol_adherence.sql`，
  已定義 `fn_expected_reports()` 並改用協定式分母——**但從未套用到 prod**，這正是 prod 仍在跑
  `max(pod)+1` 的原因。該版本**同樣帶有 join 扇出**。本次一併取代之。
  其排程編碼為「第二週偶數 POD 8/10/12/14、第三週起每週約 2 次」共 17 次，與主持人今日確認的
  「第二週每兩日、第三週起每週一次」共 13 次不同；**以主持人今日之定義為準**
  （同意書寫「第 15–30 天每週 1–2 次」，每週一次為其保守端，仍在同意範圍內）。
- **正式資料庫變更**：經 Management API 執行 `DROP VIEW` + `CREATE VIEW`。
  **不用 `CREATE OR REPLACE` 的理由**：該語法無法插入或重排欄位，而 prod 的欄位順序與 migration
  鏈已經分歧（首次嘗試即以 `42P16 cannot change name of view column` 失敗，且 CI 從零重播時
  同樣失敗）。DROP 會一併失去 grants 與 reloptions，故於同一份 migration 內重述：
  (1) `WITH (security_invoker = on)`——7/23 view RLS bypass 稽核後所加，遺漏將重新引入權限繞過；
  (2) `REVOKE ALL FROM anon` 與 `GRANT SELECT TO authenticated, service_role`。
- **驗證**：HSF-001 由 24 筆／240% 修正為 **8 筆／預期 9／88.9%**；`security_invoker=on` 仍在；
  **anon 權限為空**；`had_alerts` 行為不變。預期回報曲線逐日驗證：POD 0–7（8 次）→ 9/11/13（3 次）
  → 20/27（2 次），30 天共 13 次。migration 檔 `20260802140000_fix_adherence_view.sql` 存檔。
- **待辦（未處理，需主持人決定）**：`check-adherence` 排程函式目前對 **POD 0–30 每天**推播提醒，
  與同意書之遞減排程不一致。受試者在非回報日仍被提醒，屬與同意內容不符，且可能影響留存率。

### bug + db + 量表 · 警示謊報「連續天數」，且「肛門控制」題收到的其實是傷口分泌物
- **起點**：PI 看到 HSF-001 的警示「已連續 2 天出現滲便」，以臨床判斷質疑——該例痔瘡手術
  未觸及括約肌，不可能滲便。查證後發現**兩個獨立問題**，PI 的直覺同時命中兩個。

**問題一：警示引擎把「次回報」當成「天」**
- **根因**：`fn_check_alerts`（PL/pgSQL trigger）與 `src/utils/alerts.js`（前端）都是
  `ORDER BY report_date DESC LIMIT 7` 後**依陣列/游標位置**數連續，**從未檢查日期是否相鄰**。
  HSF-001 於 POD 7（07-31）與 POD 9（08-02）回報滲便，08-01 未回報，引擎數成「連續 2 天」。
  五條 streak 規則中有四條這樣措辭（出血那條寫「次回報」是對的，顯然有人修過一條沒修其他）。
- **為什麼不改成「檢查日期相鄰」**：本研究追蹤排程是遞減的（前 7 天每日、7–14 天隔日、
  14–30 天每週），**POD 7 之後回報本來就不該相鄰**。要求相鄰等於讓這些安全警示在 30 天
  觀察期的大部分時間失效，是反方向的失敗。故保留「數次回報」的語意，只修正措辭。
- **處置**：四條訊息改為「已連續 N **次回報**…」。前端另附實際日期區間（如「07-31 至 08-02」）
  讓空缺可見；trigger 端不加區間——那需要追蹤 streak 邊界、多動十餘行 PL/pgSQL，對 live 的
  臨床基礎設施採最小改動原則，研究者要看日期可用 7/26 建的病人逐日明細頁。
- **正式資料庫變更**：`fn_check_alerts` 經 Management API 手動 `CREATE OR REPLACE`
  （**不用 `db push`**，migration 歷史與 prod 錯位會重播全部）。patch **由 prod 自身的
  `pg_get_functiondef` 產生**、只替換四個字串，其餘 7419 字元逐字保留，確保改的是真正在跑的
  那份而非磁碟版本。已驗證：五句訊息皆為「次回報」、零殘留假宣稱、`trg_check_alerts` 仍正常
  掛載於 `symptom_reports`（tgenabled=O）。migration 檔
  `20260802120000_alert_message_report_count.sql` 存檔以使磁碟反映 prod。
- **架構債（未處理，已知）**：同一套臨床規則存在**兩份獨立實作**（JS + PL/pgSQL），會漂移。
  本次即為兩邊各修一次。長期應收斂為單一真實來源。

**問題二：「肛門控制」中間選項量到的是內褲污漬，不是控便能力**
- **根因（item validity，非 bug）**：選項描述原為「內褲有少量污漬、不自覺漏出」。痔瘡術後
  POD 7–9、傷口仍腫脹有異物感時，內褲污漬最常見的來源是**傷口分泌物**。但該選項存成 `滲便`、
  警示標題叫「持續滲便」，於是分泌物被記錄成控便問題。
- **旁證**：HSF-001 八次回報中**從未在傷口欄勾選「分泌物」**（該選項一直存在），顯示他把
  污漬報在了「肛門控制」題，因為只有那題的描述符合他觀察到的現象。
- **處置（量表變更）**：選項改為「**偶爾漏便** —— 不自覺漏出糞便、內褲沾到便漬」，並於題目
  加提示「若只是傷口分泌物或血水沾到內褲，請在下方『傷口狀況』選『分泌物』」。**不加題、

### bug · 審核佇列可能被 200 筆上限悄悄截斷
- **症狀（潛在，尚未發生）**：`getAllChatsForResearcher()` 取 `limit(200)` 且僅依 `created_at`
  倒序。一旦 `ai_chat_logs` 超過 200 列，**最舊的會被擠出視窗**——而那正是等待審核最久的那些。
  以 50 位病人 × 30 天的目標收案量，這是會踩到的。
- **為什麼要緊**：AI 回覆審核是本研究對「AI 衛教品質」的安全網。被截斷代表某則不當回覆
  可能永遠不會出現在待審清單裡，而畫面上完全沒有任何截斷提示。
- **修法**：查詢加一層排序 `.order('reviewed', { ascending: true })`（false 排在 true 前），
  未審核的一律優先進入 200 筆視窗，上限只會裁掉**已審核**的歷史。未動 `limit`。
- **測試**：新增 `src/utils/__tests__/chatReviewQueue.test.js`。用一個**真的會執行 order/limit
  語意**的假 query builder，斷言「回傳結果裡有沒有漏掉未審核紀錄」，而非斷言「有沒有呼叫
  .order()」——後者只是鏡射實作。修前紅燈：3 筆未審核全被擠出。
- **殘留限制（已知，未處理）**：若未審核數本身超過 200，仍會截斷，且頁面「待審核 N 則」
  會低報。但那個數字代表審核流程已停擺數週，屬流程問題而非顯示問題。
- **影響**：純前端查詢調整，經 Vercel 部署。

### ops + bug · 「有 API 費用但 AI 審核頁空的」——探針花費與病人用量分不開
- **症狀**：8/1、8/2 Anthropic 有費用產生，但研究者的 AI 回覆審核頁沒有任何待審訊息。
- **調查**：三張表交叉比對，結論一致——`ai_chat_logs` 全表僅 1 筆（07-23 TEST-001，已審核）、
  `ai_request_logs` 全表 12 筆全在 07-23、`audit_trail` 近 7 天零筆 `ai.chat_request`。
  再查 Supabase Edge Function 日誌（近 6 小時）：`health` 234 次、`ai-chat` **0 次**。
  即：**自 07-23 起無任何病人使用 AI 衛教**，審核頁是空的沒錯。全 repo 只有兩處呼叫
  `api.anthropic.com`（`ai-chat/index.ts`、`health/checks.ts`），故費用全數來自 health canary。
- **根因（非故障）**：canary 依設計就是真的送一次 `max_tokens:1` 生成——這正是抓「額度耗盡」
  的唯一方法。但它與 ai-chat 共用 `CLAUDE_API_KEY`，於是 console 上探針花費與病人使用花費
  **無法區分**，任何非零金額都看起來像有人在用臨床介入。約 940 次/天 ≈ US$0.02/天。
- **處置（commit `a675bc3`）**：
  1. **拆金鑰**：canary 改計費到 `HEALTH_CLAUDE_API_KEY`，未設定時 fallback 回
     `CLAUDE_API_KEY`（故未設 secret 前行為完全不變）。額度耗盡是**組織層級**，同組織同
     workspace 的第二把金鑰仍抓得到；拆開唯一失去的是「chat 金鑰被撤銷」的偵測，
     故**新增 `chat_key` 致命檢查**——用 `CLAUDE_API_KEY` 打 `GET /v1/models`，需認證但
     **零 token 費用**，把覆蓋率補回來。
  2. **補 ai-chat 盲點**：把 SSE relay 抽成 `stream.ts`（可注入、可測），並在串流中途拋錯時
     補寫 `ai_request_logs`。原本 Anthropic 已回 200、已生成、已計費，但串流斷掉那條路徑
     **三張表都不寫**——重複發生也完全看不見。同時把 metrics/audit 改為 `close()` 前
     `await`：edge isolate 可能在回應完成瞬間被回收，fire-and-forget 的 insert 會被丟掉。
  3. **審核頁標籤**：`ChatReview` 標題原寫「PAST 24H」，但查詢無時間過濾（僅 limit 200），
     等於告訴審核者相反的事。改為「最近 200 則」。
  4. **CI 跑 Deno 測試**：vitest 刻意排除 `supabase/**`（見 07-26 條目），導致 Edge Function
     測試**從來只在本機跑過**——包含守著 ai-chat 這個臨床介入的那些。新增 `edge-functions`
     job，並讓 `deploy-supabase` 依賴它。
- **驗證**：17 Deno + 390 vitest 全綠、lint 乾淨、build 通過。缺陷測試皆先看到紅燈才修
  （串流中斷案例修前 `metrics.length === 0`）。
- **影響**：前端有變更（審核頁標籤），經 Vercel 部署；Edge Functions 經 ci.yml 重新部署。
  病人端會看到一次「系統已更新」橫幅。**`HEALTH_CLAUDE_API_KEY` 尚待 PI 於 Anthropic Console
  建立並設定**——在那之前 fallback 生效，監控行為與先前完全相同。
- **待辦（需 PI 於 Better Stack 後台操作）**：探測間隔由實測的 ~90 秒改為 **5 分鐘**。設計文件
  原本就寫「pilot 可接受約 5 分鐘」，改後花費降至 1/3，以目前收案量偵測速度無實質損失。
- **教訓**：可觀測性本身會消費資源，而**共用金鑰會讓監控成本偽裝成使用量**。要回答「病人到底
  用了多少 AI」，權威來源是 `ai_request_logs`（每筆有 input/output tokens），不是 Anthropic
  console。另外：`ai_request_logs` 這種「打 API 的每條路徑都寫一列」的設計，讓「有沒有花錢」
  與「有沒有留訊息」成為兩個可獨立驗證的事實，本次不用猜就排除了「有聊天但寫入失敗」。
- **順帶記錄（研究面）**：HSF-001 已 POD 9、交了 8 份症狀日誌，AI 衛教使用次數為 **0**。
  這不是 bug，是真實 engagement 數據。
